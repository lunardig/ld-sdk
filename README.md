# ld-sdk

The Lunar Dig SDK: everything needed to write programs that play a Lunar Dig claim, with
no other repository. A **release** contains the alpha engine as binaries (Linux, macOS,
Windows and WebAssembly), the interface contract (schemas, generated types, conformance
vectors), the alpha catalog, a Python client, the TypeScript client the web game uses,
and a developer guide. Start with [`docs/guide.md`](docs/guide.md).

## Using a release

Download `ld-sdk-<version>.tar.gz` (or `.zip`) from this repository's Releases, unpack it,
and follow [`docs/guide.md`](docs/guide.md). In short:

```sh
python examples/first_controller.py --engine engine/linux-x86_64/ld-engine-cli
python tools/verify_release.py ld-sdk-<version>.tar.gz --sums SHA256SUMS   # the published file, and that it works on its own
```

On macOS, clear the download's quarantine flag first (`xattr -dr com.apple.quarantine
ld-sdk-<version>`): the engine binaries are not yet signed or notarized. See the guide, §2.

`RELEASE.json` and `engine/ENGINE.json` say exactly which commits a release was built from.

## Making a release

Run the `release` workflow from the Actions tab with a version (for example
`0.1.0-alpha.1`), or push a tag `v<version>`. It builds ld-engine at the commit in
`engine/ENGINE_REF` for every platform, packages this repository at that commit with the
pinned `vendor/ld-interfaces` (`tools/package_release.py`), checks the result from a
fresh folder with both the native and the browser engine (`tools/verify_release.py`),
and publishes it as a pre-release. It needs the `LD_ENGINE_TOKEN` secret (see the
workflow's header). To ship a newer engine, update `engine/ENGINE_REF`.

## Working in the repository

The rest of this README is for internal development in a clone, where `vendor/ld-interfaces`
is a git submodule and the engine binaries are not present.

## Quick start

```sh
git clone --recurse-submodules https://github.com/lunardig/ld-sdk
cd ld-sdk
pip install -r vendor/ld-interfaces/requirements.txt

cargo test --workspace
cargo build --release --bin ld-mock-cli
python tools/check_fixtures.py               # 58 checks over six fixtures

./target/release/ld-mock-cli < fixtures/running-loop/requests.jsonl   # watch the raw protocol

cd ts && npm ci && npm test
```

The WebAssembly build needs the `wasm32-unknown-unknown` target and `wasm-bindgen-cli` 0.2.100 (the version must match the crate's pinned `wasm-bindgen`):

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.100 --locked
./tools/build-wasm.sh
cd ts && npm test        # now also runs the wasm-vs-native comparison
```

## Using the client in a page

```ts
import { WorkerTransport, createEngine } from "@lunardig/ld-sdk";

const transport = await WorkerTransport.start({
  createWorker: () => new Worker(new URL("@lunardig/ld-sdk/worker", import.meta.url), { type: "module" }),
  bindingsUrl: "/engine/ld_mock_wasm.js",
  wasmUrl: "/engine/ld_mock_wasm_bg.wasm",
});
const engine = await createEngine(genesis, catalog, transport);
await engine.submit(command);
await engine.advanceTo("60000000");
const view = await engine.observe();
```

All quantities and times are decimal strings. Convert to numbers for display, never for anything sent back.

`createEngine` and `restoreEngine` take the transport as a third argument; LD-PEC-002 §5.2 shows them with two. Engine errors arrive as `LdEngineError` with the I-1 `code`. If the engine traps, the worker is replaced, the failing call rejects with `ENGINE_FAULT`, and the fresh engine needs a `restoreEngine` from your last snapshot.

### Without WebAssembly

`createEngineBridge` (Node) serves engine binaries over HTTP, one child process per session, and `HttpTransport` talks to it from a page. ld-web's dev server uses this to run the UI against `ld-mock-cli`, and later against a native ld-engine build. It is a development tool: bind it to localhost.

## Fixtures

| Fixture | Ends with |
| --- | --- |
| `running-loop` | Solar array powering an electrolyzer; both jobs `RUNNING` |
| `starved-input` | Electrolysis `STARVED`, `BELOW_RESTART_THRESHOLD` on water |
| `blocked-output` | Electrolysis `BLOCKED`, `BLOCKED_OUTPUT` on a full hydrogen tank |
| `lunar-night` | Irradiance 0: solar `STARVED_REQUIRE`, electrolysis `STARVED_POWER` |
| `failed-machine` | Fragile electrolyzer worn out: `FAILED` with `wear-limit.electrolyzer-1` |
| `rejected-command` | A command naming an unknown machine admitted as `REJECTED_STATE` |

`tools/check_fixtures.py` checks, for each one, that every response validates against the I-1 schema, ids echo, there are no error responses, and the expectations in `fixture.json` hold. It also checks:

- **Determinism.** Two runs give the same state hash.
- **Subdivision independence (V-05).** Splitting every advance into seven off-grid steps gives the same state hash.
- **Restore equivalence (V-09).** Snapshot, restore in a fresh engine, advance 30 s; the result equals the uninterrupted run.

`cargo test` runs the same properties in-process. `npm test` replays the fixtures through the TypeScript API. When `ts/wasm` exists it also requires the wasm and native builds to return byte-identical responses to every request.

## What the mock simplifies

The mock implements I-1 exactly and the physics loosely (LD-PEC-002 §6). It exists so W4 can build the UI now. Its numbers are not a preview of game balance.

- **Time.** Advances in 1-second ticks on a grid anchored at genesis, which makes subdivision independence hold by construction. With no job eligible it jumps straight to the next environment change.
- **Primitives.**
  - REACT, WORK, ENERGY, WEAR and REQUIRE act as specified.
  - PARTITION, COMBINE, PHASE, ASSEMBLE, LOSS and DWELL are accepted but move nothing.
  - BATCH processes run like FLOW.
- **Power.** There is one implicit electrical bus with no storage. Producers run first, then consumers in priority order; a consumer short of power stalls with `STARVED_POWER`.
- **Material.** Connections move material instantly. Each buffer holds a single lot, `<buffer>.lot`.
- **Commands.** Apply at the current time only; other times return `REJECTED_TIME` (`mock-current-time-only`).
- **Restore.** Restores only mock snapshots. Applied command ids are not kept, so resubmitting an id after a restore is not detected.
- **Mock-only state.** Claim constants (grid origin, active environment functions) and job stall reasons are stored as pending events of mock-only kinds (`genesis-start`, `environment`, `started`, `restart-wait`, `why.*`). The real engine will not produce these.

## CI

`.github/workflows/ci.yml` runs clippy, the Rust tests, a fixture regeneration diff, the Python checks and the TS tests on the native mock. It then builds the wasm and requires the wasm-vs-native comparison to run without skipping.

`vendor/ld-interfaces` is private. CI checks out ld-sdk with the default workflow token and fetches the submodule with a repository secret `LD_INTERFACES_TOKEN`: a fine-grained token owned by lunardig with Contents: read on `lunardig/ld-interfaces` only.

## Examples

`examples/loop_controller.py` is an external controller that plays *The loop* (the
final ld-web challenge, LD-PEC-006 §3.1) over I-1 against any engine speaking the line
protocol. It builds the mining chain from kits, makes iron, fabricates a hopper and
installs it, then keeps the plant working through the lunar night on fission or on the
fuel cell. It exits 0 when both goals hold; ld-engine's CI runs it.

    python examples/loop_controller.py --engine ../ld-engine/target/release/ld-engine-cli --night fuel-cell --report

`examples/controllers/` holds three browser controllers for a claim running in the game's
host window, over ldcp-0 (LD-PEC-009; guide §8): a spreadsheet (`read`, `operate`), a
schematic (`read`, `build`) and a scripted operator that pauses power-starved jobs at dusk
(`read`, `operate`). ld-web's UI suite runs all three from three origins against one claim.

    (cd ts && npm run build) && node examples/controllers/serve.mjs 5174
